# ADR 0002 — Шариста архітектура та правила залежностей

- **Статус:** Прийнято
- **Дата:** 2026-11-24
- **Ухвалювачі:** команда

## Контекст

Обравши модульний моноліт (ADR 0001), ми потребуємо мінімального, забезпечуваного
розшарування, щоб код лишався зрозумілим, а модулі згодом можна було виокремити в
сервіси без «археології». Хочемо уникнути класичної проблеми, коли обробники
маршрутів звертаються безпосередньо до бази даних і бізнес-правила протікають в
HTTP-код.

## Рішення

Кожен модуль організовано в три шари, і залежності вказують **лише вниз**:

```
api/      (HTTP: маршрути, розбір запиту, мапінг DTO, коди статусів)
  │  залежить від
  ▼
service/  (сценарії: валідація, оркестрація, мапінг DTO ↔ домен)
  │  залежить від
  ▼
domain/   (сутності, value objects, інваріанти, доменні помилки)
```

Наскрізні технічні задачі живуть у `infra/` і використовуються під час збирання в
`app.js`, а не доменом.

### Що де лежить

- **`api/`** — роутери Express. Відповідає за:
  - читання `req.params`, `req.body`, заголовків;
  - виклик одного методу сервісу;
  - формування відповіді та HTTP-статусу;
  - додавання `requestId` у тіло.
  Тут **немає бізнес-правил** і **немає SQL**.

- **`service/`** — сценарії. Відповідає за:
  - валідацію входу через домен (наприклад, `Link.create`);
  - оркестрацію збереження через підготовлені запити;
  - мапінг рядок ↔ доменна сутність ↔ об'єкт відповіді;
  - кидання типізованих доменних помилок (`ValidationError`, `NotFoundError`, ...).

- **`domain/`** — чиста логіка. Відповідає за:
  - сутності (`Link`, `Item`) та їхні інваріанти;
  - правила валідації (формат URL, формат slug, тип title);
  - типи доменних помилок.
  Він **нічого не знає** про Express, HTTP чи SQL.

- **`infra/`** — ініціалізація бази даних, request-id, rate limit, chaos,
  middleware помилок. Використовується в корені композиції (`src/app.js`) і
  ніколи не імпортується доменом.

## Напрямок залежностей

```
api  ──►  service  ──►  domain
 │                        ▲
 └──►  infra (middleware) ┘   (infra може використовуватись у збиранні та api, ніколи — доменом)
```

- Залежності течуть **від більш мінливого (HTTP) до більш стабільного (домен)**.
- Домен не залежить ні від чого в цьому проєкті.

## Заборонені зв'язки (забезпечується рев'ю)

1. `api/` **не повинен** імпортувати базу даних чи виконувати SQL. Увесь доступ до
   даних іде через `service/`.
2. `api/` **не повинен** містити логіку валідації; валідація належить `domain/`
   (викликається з `service/`).
3. `domain/` **не повинен** імпортувати `express`, `node:sqlite` чи будь-що з
   `infra/`, `service/` або `api/`.
4. `service/` **не повинен** імпортувати `express` чи торкатися `req`/`res`.
5. Модулі **не повинні** читати таблиці одне одного напряму; вони спілкуються через
   інтерфейс сервісу (а згодом — через HTTP-контракт).

## Наслідки

**Позитивні**

- HTTP-задачі та бізнес-правила розвиваються незалежно.
- Домен тривіально тестується юніт-тестами (див. `tests/link.service.test.js`).
- Кожен шар має очевидне місце, що тримає pull request'и малими й зручними для рев'ю.

**Негативні / компроміси**

- Більше файлів, ніж у «сервері в одному файлі».
- Простий CRUD проходить через три шари, що може здаватися церемонним — прийнято як
  свідома ціна навчання.

## Перевірка

- `tests/link.service.test.js` вправляє `service/` з in-memory базою даних і ніколи
  не імпортує Express.
- Пункт чеклиста рев'ю: «Чи імпортує `domain/` щось поза `domain/`?» — відповідь
  має бути «ні».
