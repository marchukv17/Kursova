# ADR 0003 — Стиль API та модель помилок

- **Статус:** Прийнято
- **Дата:** 2026-11-24
- **Ухвалювачі:** команда

## Контекст

Модуль Links надає HTTP API, який споживає браузерний клієнт і, згодом, інші
сервіси. Потрібен послідовний стиль REST, єдина форма помилок і політика кодів
статусів, щоб клієнти однаково обробляли збої (це також живить роботу зі стійкості
в лаб. 5).

## Рішення

### Стиль REST

- Ресурси — **іменники в множині**: `/links`, `/items`. Без дієслів у шляхах.
- `POST /links` створює; `GET /links` перелічує; `GET /links/{id}` читає один;
  `PUT`/`PATCH /links/{id}` оновлюють; `DELETE /links/{id}` видаляє.
- Приймаються і `PUT`, і `PATCH`. `PUT` трактується як повна заміна **змінюваних**
  полів; `PATCH` — як часткове оновлення. Незмінний `slug` не змінюється жодним із
  них.
- Запити й відповіді використовують `application/json`. `DELETE` завершується
  успішно з `204 No Content`.
- `GET /{slug}` — єдиний навмисний не-ресурсний маршрут: він виконує редірект
  (`302`), що є метою продукту.
- Тіла JSON використовують **camelCase** і **DTO**, а не доменні об'єкти. DTO — це
  простий об'єкт передачі даних, сформований під контракт, без бізнес-логіки.

### Політика кодів статусів

| Ситуація                            | Статус |
|-------------------------------------|--------|
| Успішне читання / оновлення         | `200`  |
| Ресурс створено                     | `201`  |
| Успішне видалення                   | `204`  |
| Редірект на оригінальний URL        | `302`  |
| Помилка валідації (поганий вхід)    | `400`  |
| Відсутня/недійсна автентифікація (майбутнє) | `401` |
| Ресурс не знайдено                  | `404`  |
| Конфлікт slug (порушення унікальності) | `409` |
| Перевищено rate limit               | `429`  |
| Неочікувана серверна помилка        | `500`  |
| Тимчасовий збій (безпечно повторити)| `503`  |

Відповіді `429` містять заголовок `Retry-After`. `503` сигналізує про тимчасовий
збій, який клієнт може повторити з backoff.

### Єдина форма помилки

Кожне тіло помилки має саме таку форму:

```json
{
  "error": "ValidationError",
  "code": "ORIGINAL_URL_REQUIRED",
  "details": [{ "field": "originalUrl", "message": "originalUrl is required" }],
  "requestId": "8f14e45f-ea3d-4f0b-9c3a-6c1a2b3d4e5f"
}
```

- `error` — стабільний, зрозумілий людині клас помилки (`ValidationError`,
  `NotFound`, `Conflict`, `too_many_requests`, `internal_error`, ...).
- `code` — машинозчитуваний, стабільний код (`ORIGINAL_URL_REQUIRED`,
  `SLUG_TAKEN`, `LINK_NOT_FOUND`, `RATE_LIMITED`, ...). Може бути `null`.
- `details` — необов'язковий масив `{ field, message }` для помилок валідації.
- `requestId` — дублює заголовок відповіді `X-Request-Id` для кореляції.

`details` присутній завжди (можливо, `null`), щоб клієнти могли покладатися на ключ.

### Заголовок кореляції

Кожна відповідь містить `X-Request-Id`. Якщо клієнт надав його — він дублюється;
інакше сервер генерує UUID. Це обов'язково для всіх ендпоїнтів, включно з помилками.

### Ідемпотентність

`POST /links` поважає заголовок `Idempotency-Key`. Два запити з тим самим ключем
повертають той самий ресурс (той самий `id`); другий не створює дубля. Якщо
заголовка немає, запит обробляється звичайно (неідемпотентно).

### Відповідність OpenAPI

`docs/api/openapi.yaml` — єдине джерело істини для публічного API. Правила:

- Кожен ендпоїнт, тіло запиту, відповідь і помилка описані в специфікації.
- Pull request, що змінює поведінку, **повинен** оновити специфікацію в тому ж PR.
- Специфікація має проходити валідацію в Swagger Editor
  (https://editor.swagger.io/) до злиття; відрендерений результат збережено як
  `docs/api/swagger_screenshot.png`.
- README посилається на специфікацію та вставляє скріншот у розділі
  «Документація API».

## Розглянуті альтернативи

- **GraphQL.** Відхилено: надмірно для кількох ресурсів і ускладнило б навчання
  HTTP-статусам та обробці помилок.
- **Довільні рядки помилок.** Відхилено: клієнтам потрібна стабільна, розбірна
  модель помилок, щоб реалізувати ретраї та режим деградації.
- **Вбудовування Swagger UI у застосунок.** Відкладено: завдання вимагає
  валідувати контракт зовні, а не обслуговувати UI.

## Наслідки

**Позитивні**

- Клієнт може надійно розгалужуватися за `code` та `requestId`.
- Ретраї й обробка rate limit (лаб. 5) реалізуються просто.
- Контракт можна переглядати незалежно від коду.

**Негативні / компроміси**

- Синхронізація YAML із кодом вимагає дисципліни (забезпечується на рев'ю).
- Трохи багатослівне тіло помилки для дуже дрібних помилок — прийнято заради
  послідовності.
