# ADR 0001 — Стиль архітектури: модульний моноліт

- **Статус:** Прийнято
- **Дата:** 2026-11-24
- **Ухвалювачі:** команда

## Контекст

LinkForge — невеликий скорочувач URL, що створюється під час курсу. Команда мала,
домен вузький (створити посилання, розв'язати slug, рахувати кліки), а ціль
розгортання — одна машина з `npm start`. Ми на етапі (лаб. 4), коли треба свідомо
обрати між **модульним монолітом** і **пілотними мікросервісами**.

Обмеження, що мають значення:

- Один репозиторій, один процес, одна база SQLite.
- Немає операційної платформи для service discovery, шлюзів чи розподіленого
  трасування.
- Головна мета зараз — навчитися чистим межам і явному контракту API, а не
  оптимізувати незалежне масштабування.
- Домен уже підказує природні шви (Links, Items, майбутні Identity й Analytics),
  але ці шви можна виразити як *модулі*, а не як *сервіси*.

## Рішення

Ми залишаємо **модульний моноліт**. Один розгортуваний процес Express містить
кілька логічних модулів, кожен зі своїми зрізами `api/`, `service/` і `domain/`.
Модулі взаємодіють через in-process інтерфейси, ніколи через базу даних і ніколи
не заглядаючи у внутрішні реалізації одне одного.

Модулі сьогодні:

- **Links** (ядро) — `src/api/links.routes.js`, `src/service/link.service.js`,
  `src/domain/Link.js`.
- **Items** (підтримувальний, демо лаб. 1) — власні routes/service/domain.
- **Health** — наскрізний операційний модуль.

Поверхня API, як і раніше, описана єдиним `docs/api/openapi.yaml`, який
майбутнє розбиття на сервіси збереже як контракт.

## Розглянуті альтернативи

1. **Пілотні мікросервіси вже зараз.** Відхилено на цьому етапі: це додало б
   міжпроцесні виклики, мережеві режими відмов, скрипти розгортання й дублювання
   конфігурації, поки домен ще змінюється. Операційна ціна не виправдана жодною
   реальною потребою масштабування.
2. **Єдиний неструктурований моноліт (без модулів).** Відхилено: це зробило б
   пізніше виокремлення сервісів дорогим і розмило б межі домену, які ми явно
   намагаємося засвоїти в лаб. 3.

## Наслідки

**Позитивні**

- Проста локальна розробка: `npm install && npm start`.
- In-process виклики легко осмислити й тестувати.
- Межі домену все ще явні, тож пізніше виокремлення — це рефакторинг, а не
  переписування.
- Одна транзакція БД може безпечно охопити агрегат одного модуля.

**Негативні / компроміси**

- Модулі ділять один процес і один файл бази даних; збій впливає на все.
- Немає незалежного масштабування чи незалежного розгортання кожного модуля.
- Спільна SQLite поки не дає ізоляції даних на рівні сервісів (пом'якшується
  правилами шарів з ADR 0002 і тим, що кожен модуль тримає свої таблиці приватними).

## Коли переглядати

Перегляньте це рішення, коли **будь-яке** з наведеного стане істинним:

- Два модулі потребують незалежного масштабування (наприклад, редіректи отримують
  значно більше трафіку, ніж створення посилань).
- Модуль потребує іншого середовища виконання чи мови.
- Команда зростає настільно, що єдине розгортання стає вузьким місцем координації.
- Потрібна незалежна частота релізів для кожного модуля.

Під час перегляду контракт OpenAPI лишається тим самим, а зріз `api/service/domain`
кожного модуля стає насінням окремого сервісу.
