## Бізнес-документ — що містить

`docs/business_doc.md` дотримується запитаної структури:

1. **Назва й короткий опис** — три абзаци про те, що таке LinkForge, для кого він і
   що віддає перевагу надійності над широтою функцій.
2. **Користувачі та ролі** — Відвідувач, Творець, Оператор плюс дві майбутні ролі
   (Адміністратор, Власник).
3. **Основні сценарії використання** — п'ять сценаріїв: створити коротке
   посилання, перейти за ним, безпечно повторити, переглянути/керувати
   посиланнями, пережити перевантажений бекенд.
4. **Функціональні вимоги** — дванадцять пронумерованих вимог (FR-1 … FR-12), від
   `GET /health` до ідемпотентного створення, кореляційних id, rate limit і єдиної
   форми помилки.
5. **Нефункціональні вимоги** — швидкодія, надійність, безпека, зручність,
   спостережуваність, супровідність, портативність.
6. **Обмеження** — явний список «система НЕ робитиме»: без автентифікації, без
   терміну дії, без аналітичних дашбордів, без власних доменів, без білінгу, без
   розподіленої інфраструктури.

Писати розділ обмежень першим було корисно: це зупинило розповзання обсягу й
зробило roadmap чесним.

## Діаграма архітектури — що показує

Діаграма містить обов'язковий мінімум **Client → Backend → Database** і додає
майбутні модулі:

- **Client (Browser)** — `public/index.html`, `public/app.js`; завантажує items,
  створює посилання й відповідає за UI режиму деградації. З'єднується з бекендом
  через HTTP/JSON.
- **Backend (Node.js + Express)** — один процес із трьома шарами, намальованими як
  вкладені блоки: `api/` (контролери, мапінг DTO, коди статусів, `X-Request-Id`),
  `service/` (сценарії, валідація, мапінг DTO ↔ домен) і `domain/` (сутності та
  інваріанти). Стрілки показують, що `api/` викликає `service/`, який викликає
  `domain/` — це in-process виклики, а не мережеві.
- **Database (SQLite)** — `node:sqlite` у режимі WAL, таблиці `items` і `links`,
  доступ лише через підготовлені запити з шару сервісу.
- **Майбутні модулі (пунктир)** — **Auth Service** (токени, власність),
  **Analytics** (події кліків, статистика) і **Notifications** (email/webhooks).
  Вони пунктирні й з'єднані пунктирними стрілками, що сигналізує «заплановано, не
  реалізовано».

Кожен блок пояснено словами в легенді внизу зображення та в README, що задовольняє
вимогу «пояснити, що означає кожен блок».

## Roadmap — що планує

`docs/roadmap.md` охоплює наступні чотири тижні:

- **Тиждень 3** — новий ендпоїнт `GET /links/{id}/stats` для аналітики кліків, із
  тестами й оновленням OpenAPI.
- **Тиждень 4** — мінімальна автентифікація (`Bearer`-токен) і `ownerId` на
  посиланнях, за інтерфейсом `Auth`.
- **Тиждень 5** — зміцнення CRUD: м'яке видалення, пагінація, тести на конфлікт
  slug.
- **Тиждень 6** — спостережуваність і полірування: корельовані логи, заглушка
  `/metrics`, ідемпотентність у БД із TTL і наскрізний HTTP-тест.

Також є беклог (термін дії, власні домени, QR-коди, виявлення зловживань) і
короткий список ризиків (зберігання ідемпотентності, обмеження SQLite, обсяг
автентифікації).

## Команда та Git-процес

Лабораторна передбачає, що документ розподіляють між учасниками через форки та pull
request'и. Задуманий розподіл:

- Лідер створює папку `docs/` і каркас `business_doc.md`.
- Один учасник відповідає за діаграму архітектури (`architecture_diagram.png`).
- Один учасник відповідає за roadmap (`roadmap.md`).
- Один-два учасники пишуть розділи вимог і обмежень.

Кожна зміна надходить як pull request із форку; лідер зливає після швидкого рев'ю
(структура повна? посилання валідні? зображення читабельне?).

## Як переглянути артефакти

1. Відкрийте `docs/business_doc.md` і переконайтеся, що присутні всі шість
   розділів.
2. Відкрийте `docs/architecture_diagram.png` і переконайтеся в потоці
   Client → Backend → Database плюс принаймні один майбутній модуль.
3. Відкрийте `docs/roadmap.md` і переконайтеся, що тижні 3–6 мають конкретні,
   постачальні пункти.
4. Перевірте, що README посилається на ці файли.
