# Лабораторна 3 — Domain-Driven Design: моделювання домену

## Мета

Почати архітектуру з бізнес-домену, а не лише з технічних шарів: поділити проєкт
на піддомени, визначити bounded contexts, побудувати контекстну карту, написати
глосарій ubiquitous language та прототипувати ключові сутності в коді.

## Крок 1 — Поділ проєкту на піддомени

Скорочувач URL розкладено на такі піддомени:

- **Links (ядро).** Причина існування продукту: створити посилання, розв'язати
  slug, зробити редірект, порахувати кліки. Саме тут найбільше бізнес-цінності й
  найбільше зусиль із моделювання.
- **Items (підтримувальний).** Крихітний каталог лише для читання, використаний у
  лаб. 1 для доведення конвеєра «клієнт → бекенд → база даних». Він лишається
  окремим контекстом, щоб ніколи не протікав у ядро.
- **Identity (загальний, майбутній).** Користувачі та акаунти. Загальний, бо це
  добре зрозуміла проблема, яку радше запозичити, ніж винаходити.
- **Analytics (майбутній).** Споживає події кліків для побудови звітів. Він не
  володіє посиланнями; лише читає події, які публікує контекст Links.
- **Notifications (майбутній).** Реагує на події закінчення терміну дії посилань і
  надсилає повідомлення.

## Крок 2 — Ключові сутності кожного піддомену

- **Links:** `Link` (корінь агрегату), `Slug` (value object), `ClickCounter`
  (value object).
- **Items:** `Item`.
- **Identity:** `User` (заплановано).
- **Analytics:** `ClickEvent`, `Report` (заплановано).

Атрибути й поведінка задокументовані в `docs/domain/entities.md`. Наприклад, `Link`
несе `id`, `slug`, `originalUrl`, `title`, `clicks`, `createdAt`, `updatedAt` і
володіє інваріантами «originalUrl — валідний URL http(s)» та «slug унікальний і
незмінний».

## Крок 3 — Ubiquitous language

`docs/domain/glossary.md` визначає спільний словник з **одним значенням на термін у
межах контексту**. Ключове:

- **Link** — агрегат; те, що створюють/читають/оновлюють/видаляють.
- **Slug** — короткий ідентифікатор (3–32 символи, `[A-Za-z0-9_-]`, унікальний,
  незмінний).
- **Short link** — повний публічний URL, похідний від базового URL і slug; не
  зберігається.
- **Original URL** — призначення, на яке розв'язується slug.
- **Redirect / resolve** — перетворення slug у редірект.
- **Click / click counter** — одне успішне розв'язання; монотонний лічильник.

Глосарій явно усуває конфлікти термінів:

- **Item** означає лише демо-рядок лаб. 1, ніколи — посилання.
- **User** (Identity) vs **Owner** (непрозорий `ownerId`, який зберігає Links).
- **Event** ніколи не вживається окремо; це або **click** (Links), або
  **ClickEvent** (Analytics).

Ці розмежування важливі, бо та сама людина є «User» для Identity і «Owner» для
Links, і ці контексти не повинні імпортувати моделі одне одного.

## Крок 4 — Контекстна карта

`docs/domain/context_map.png` показує bounded contexts та їхні зв'язки:

- **Links Context (ядро)** — центральний блок із `Link`, `Slug`, `ClickCounter` і
  ключовими дієсловами create / resolve / redirect.
- **Items Context (підтримувальний)** — незалежний; явно «без залежності від
  Links».
- **Identity Context (майбутній)** — вище за потоком від Links; постачає `ownerId`
  через anti-corruption layer (upstream → downstream).
- **Analytics Context (майбутній)** — нижче за потоком, споживач подій
  `LinkClicked`.
- **Notifications Context (майбутній)** — споживає події закінчення терміну дії.

Карта також містить невелику легенду «core language», щоб діаграма була зрозуміла
сама по собі.

## Крок 5 — Прототип моделі в коді

Прототип живе в `src/domain/`:

- **`Link.js`** — сутність `Link` плюс правила валідації, що захищають її
  інваріанти:
  - `Link.create(input)` валідує `originalUrl` (абсолютний http/https),
    `slug` (необов'язковий, перевіряється формат) і `title`.
  - `Link.update(existing, patch)` валідує змінювані поля й зберігає slug
    незмінним.
  - `Link.fromRow(row)` відновлює з рядка бази даних.
  - `toJSON()` мапиться в DTO відповіді.
- **`Item.js`** — сутність `Item` (`id`, `name`) з `fromRow` / `toJSON`.
- **`errors.js`** — типи доменних помилок (`ValidationError`, `NotFoundError`,
  `ConflictError`), що несуть стабільний `code` і необов'язкові `details`.

Ключове: доменні класи **не імпортують нічого** з Express чи SQLite. Вони — чиста
логіка й покриті тестами рівня service/.

## Як це формує код

Шар сервісу (`src/service/link.service.js`) оркеструє збереження, але делегує
кожне правило домену: викликає `Link.create` для валідації, генерує slug за
потреби й кидає типізовані помилки домену. Шар API лише мапить HTTP у виклики
сервісу. Це і є результат «спершу домен, потім шари», якого прагне лабораторна.

## Результат

Проєкт тепер структуровано за бізнес-доменом, а не лише за технічними шарами.
Ядро (`Link`) ізольоване від підтримувальних і майбутніх контекстів, словник
записано й розмежовано, а модель прототиповано чистим кодом, який уже
використовує решта системи.

## Висновок

Моделювання спершу прояснило дві речі, які інакше спричинили б баги пізніше: що
**slug** і **short link** — різні поняття, і що **item** та **link** не можна
змішувати. Обидва правила тепер видно в глосарії, контекстній карті й структурі
коду.
